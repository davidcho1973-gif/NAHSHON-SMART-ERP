# 기성 근거 대장 — 첫 적용 안내

## 목적과 기준

기존 문서함·현장보고·사진·기성 원장을 연결하여 계약 항목별로 청구 이유를 설명한다.
견적용 `boq_items`는 수정 가능한 산출자료이므로 계약 확정의 정본으로 사용하지 않는다.
`contract_boq_lines`는 수주 계약의 상업 조건, `claim_work_records`는 원문 주장·실제 보고·예상,
`pay_application_allocations`는 기존 `pay_applications`에 배정한 확인수량과 제출 근거다.
기존 `BillingCalculator`가 유보금·청구 누계·지급 청구액을 계속 계산한다.

## 사용 순서

1. 기성 청구·수금에서 수주 계약을 열고 **기성 근거 대장**으로 들어간다.
2. 원본 엑셀과 도면을 기존 문서함의 해당 프로젝트·계약에 등록한다.
3. **원본 청구자료 가져오기**에서 두 원본 문서와 준비한 JSON을 선택한다.
   문서의 SHA256·접근 범위·통화·계약액을 확인한다. 오류가 있으면 모든 행을 롤백한다.
4. 가져온 내역은 **계약 조건 확인 전 / 원문 청구 / 실적 미확인**이다.
   원문 기록은 실적으로 전환하거나 승인할 수 없다. 실제 작업은 실제 작업일·위치·수량으로 따로 기록한다.
5. 계약 원문과 위치, 지급 조건 확인 내용을 넣어 BOQ 조건을 확정한다.
   제작·반입·설치 기성은 계약상 단계별 인정 비율을 명시하며 합계는 100%다.
6. 기존 문서·현장 원문·사진을 연결한다. 담당자가 확인수량과 검토 사유를 기록한다.
   보고 20m 중 15m를 확인할 수 있으며 5m는 미확인으로 표시한다.
   5m를 나중에 확인하려면 미청구 단계에서는 검토 재개 후 수정하고,
   이미 청구한 기록이라면 남은 5m를 별도 실제 작업 기록으로 명확히 구분한다.
7. **기성 초안 생성**은 확인된 실제 작업 중 미배정 수량을 기존 기성 회차에 배정한다.
   초안을 다시 계산해도 같은 수량을 두 번 예약하지 않는다.
8. 기존 기성 원장에서 묶음을 검토한 후 제출·원청 승인·입금 배분을 기록한다.
   제출은 ERP 상태 기록이며 외부 발송을 자동 실행하지 않는다.
   근거 묶음을 인쇄/PDF 저장하거나 JSON으로 내려받을 수 있다.

## 원본 자료의 의미

청구된 항목만 가져온 자료는 부분 대장이다. 전체 계약 BOQ나 실제 검측 완료자료가 아니다.
원본 기간에 Forecast가 표시되어 있으므로 예상 포함 여부를 보존한다.
원본 금액은 공사기성 + 선급금 − 유보금 = 지급 청구액 구조로 별도 표시한다.
가져오기에서는 이 요약을 출처 정보로 보관하고 기성·입금 원장을 만들지 않는다.
원본의 공종별 절사·천 달러 절사와 시스템의 항목별 계산합은 구분하여 표시한다.

- PDF의 명시 항목 목록에서 찾지 못한 BOQ에는 도면 연결을 만들지 않는다.
- 제작 청구는 설치 실적과 구분한다. 계약의 단계별 지급 비율은 별도로 확인한다.
- 도면에 적힌 사진 ID는 실제 사진 파일이 아니다. 없는 증빙을 생성하거나 검토 완료로 표시하지 않는다.
- 파일을 다시 가져와도 기존 검토와 수량을 덮어쓰지 않는다.

## 접근·보존·계산

- 기존 기성 조회/관리 권한과 계약의 회사·현장 범위를 사용한다. 개인 문서는 공유 근거로 사용할 수 없다.
- 실제 기록은 미래 날짜를 거부한다. 예상·원문 청구 기록은 기성 계산에서 제외한다.
- 계약수량과 단계별 수량 상한, 계약 전체 금액 상한, 중복 보고 및 중복 배정을 검사한다.
- 확인·초안·제출 시 증빙 파일 존재 여부와 해시를 검사한다. 검토 후 원문 교체도 탐지한다.
- 배정된 수량·단가·검토 이력·증빙·계약 근거는 회차별로 보관한다. 한 번 제출한 묶음은 수정·삭제하지 않는다.
- 연결된 증빙은 파일 삭제 전에 차단한다. 새 공정/상황실 사진은 원본과 화면용 축소본을 분리 보존한다.
- 기존 축소본은 원본으로 복원되지 않는다. 상황실의 기존 가용 사본은 `available_copy`로 구분한다.
- 사진·문서 저장소는 기존 durable disk 설정을 사용한다. 웹 공개 폴더에 증빙을 쓰지 않는다.

## 첫 적용에서 명시적으로 제한한 부분

과거에 수동 총액으로 청구한 계약은 BOQ별 기청구 수량 대사 없이 자동 초안을 만들 수 없다.
변경계약은 명확한 계약 조건과 별도 항목으로 관리한다. 제출 후 감액·배정 취소·개별 항목별 원청 인정수량
대사는 후속 구현 대상이다. 기존 원청 인정액/수금 기능은 계속 사용한다.
선급금과 원본의 절사 조정은 출처 요약으로 보존하며 확인된 시공분 자동 계산에 혼합하지 않는다.
현장 작업자는 기존 보고를 계속 사용하고, 이번 파일럿에서는 기성 담당자가 근거 대장에서 보고와 수량을 연결한다.
현장앱 자동 BOQ 추천·모바일 전용 수량 입력·전체 상황실 KPI 재편은 아직 적용하지 않았다.

## 운영자용 가져오기 명령

배포 후 `php artisan migrate --force`가 먼저 완료되어야 한다. 기본 명령은 파일·계약 접근 점검만 한다.
아래 ID와 경로는 운영자의 실제 계약·담당자·원본 경로로 지정한다. 사용자 개인 파일을 코드 저장소에 넣지 않는다.

```sh
php artisan claims:import-source CONTRACT_ID source.json original.xlsx markup.pdf --user=MANAGER_ID
php artisan claims:import-source CONTRACT_ID source.json original.xlsx markup.pdf --user=MANAGER_ID --apply
```

`--apply`는 원본을 기존 비공개 문서 저장소에 보존하고 원문 청구 대장만 만든다.
실제 검측·계약 승인·청구 제출·입금 기록을 만들지 않는다. 테스트는 반드시 별도 PostgreSQL DB에서 실행한다.

## 계약서 전체 올리기 — 기성 = 공정 (2026-09-25)

사장 지시: «계약서의 줄이 곧 일의 단위다. 기성관리가 공정관리다.» 청구된 줄만 가져오는 위의 원본 청구 가져오기와 달리,
공정별 도면 화면의 **계약서 올리기**는 원청 계약 기성표의 **모든 줄**을 확정 계약 조건으로 올린다.

- 섹션 경계는 계약서 요약표의 수식(`=C44` 제목 행, `=K49` 소계 행)이 가리키는 대로 자른다. 섹션마다 줄 금액의 합이
  계약서 소계와 다르면 올리지 않는다. 계약 금액과 줄 합계의 차이(천 달러 절사)는 줄로 만들지 않고 화면에 차이로 보인다.
- 줄 번호는 계약서 ITEM NO(`B` 열). 원본 청구 가져오기로 이미 있는 같은 번호 줄은 수량·단가·단위가 같으면 이어 쓰고,
  다르면 전체를 멈춘다 — 계약 변경은 RFI 로만.
- 줄은 `work_section_id` 로 공정에 매달린다. 규격(D), 섹션 안 소제목, 자재·노무·경비 단가(G·H·I)는 칸으로 보존한다.
- 원청이 설치 전 반입 자재를 기성으로 인정하므로 자재·노무 단가가 둘 다 있는 줄은 `milestone`
  (`stored` = 자재 단가 비율, `installation` = 나머지). 한쪽만 있는 줄은 `quantity`.
- 공정별 진행률과 금액은 `ClaimEvidenceService::progressByLine` 이 대장과 같은 규칙으로 계산한다.
- 아직 없는 것: 청구서 엑셀 내보내기(반입 자재 칸 분리·유보금·선급금 상계·천 달러 절사), 송장 사진·상황실 글에서
  반입/설치 기록 제안, 도면 위 표시. 초안 금액은 지금 `this_period_amount` 한 칸이며 청구서 형식으로 나누는 일은 내보내기에서 한다.
